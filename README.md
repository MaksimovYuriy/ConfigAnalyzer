# ConfigAnalyzer

CLI-утилита на Go для поиска небезопасных настроек в YAML и JSON с неизвестной
структурой: debug-логирования, открытых паролей, отключённого TLS и проверки
сертификатов, прослушивания всех IPv4-интерфейсов и небезопасных алгоритмов.

## Требования

- Go 1.27.3 — версия проекта закреплена в `go.mod` и `.tool-versions`.
- Доступ к сети при первой загрузке зависимостей из `go.mod`.
- Для приведённых команд — Bash в Linux/macOS или WSL в Windows.

Go устанавливается по [официальной инструкции](https://go.dev/doc/install).
Все команды ниже выполняются из корня проекта.

## Быстрый запуск

После клонирования репозитория выполните:

```sh
cd ConfigAnalyzer
go version
go mod download
mkdir -p bin
go build -o bin/config-analyzer ./cmd/analyzer
./bin/config-analyzer examples/safe.yaml
```

Ожидаемый вывод и код завершения `0`:

```text
Анализ завершён. Проблем не найдено.
```

## Проверка своего конфига

YAML и JSON определяются по содержимому, расширение файла не используется:

```sh
./bin/config-analyzer /path/to/config.yaml
./bin/config-analyzer /path/to/config.json
./bin/config-analyzer --stdin < /path/to/config.yaml
```

Возможен ввод конфига через прямой ввод (для завершения - Ctrl+D):

```sh
./bin/config-analyzer --stdin
{
    your-config
}
```

| Аргумент или флаг | Назначение |
| --- | --- |
| Первый позиционный аргумент | Путь к одному конфигурационному файлу |
| `--stdin` | Читать конфигурацию из stdin вместо файла |
| `-s`, `--silent` | Выводить находки, но завершаться с кодом `0` при их наличии |
| `-h`, `--help` | Показать справку |
| `--` | Завершить разбор флагов, например перед именем файла с дефисом |

Файл и `--stdin` взаимоисключающие. Флаги можно передавать до или после пути:

```sh
./bin/config-analyzer examples/insecure.yaml --silent
```

| Код завершения | Значение |
| --- | --- |
| `0` | Находок нет либо находки есть, но указан `--silent`; также вывод справки |
| `1` | Найдена хотя бы одна проблема |
| `2` | Ошибка аргументов, чтения, разбора или вывода; даже при `--silent` |

Отчёт выводится в stdout, ошибки приложения — в stderr. Для точного кода
завершения используйте собранный бинарник: `go run` может возвращать свой код.

## Воспроизведение результатов

```sh
./bin/config-analyzer examples/debug.yaml
echo $?
```

Ожидается одна находка и затем код `1`:

```text
LOW: services[0].logging.level: Логирование в debug-режиме. Поменяйте уровень логирования на info или выше.
1
```

`examples/insecure.yaml` даёт шесть находок: debug-логирование, открытый пароль,
адрес `0.0.0.0`, отключение TLS, отключение проверки сертификатов и MD5.
`examples/safe.yaml` не даёт находок. Оба файла содержат демонстрационные данные.

Автоматическая проверка примеров и кодов завершения:

```sh
bash scripts/smoke.sh ./bin/config-analyzer
```

Успешный запуск заканчивается строкой `Smoke checks passed.`. В ходе проверки
намеренно выводятся находки и ошибки неверного ввода; сам скрипт возвращает `0`,
только если все коды совпадают с ожидаемыми.

## Тесты и CI

Локальные проверки:

```sh
go mod verify
gofmt -l cmd internal pkg
go vet ./...
go test -race -count=1 -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
bash scripts/smoke.sh ./bin/config-analyzer
```

Команда `gofmt -l` должна ничего не вывести. Race detector требует доступный
C-компилятор и включённый CGO; на стандартном GitHub runner это предусмотрено.
Для обычной сборки утилиты C-компилятор не нужен.

## Структура

```text

cmd/app/               общая точка входа REST и gRPC
internal/app/          запуск и остановка обоих серверов
internal/controller/restapi/ маршрут и обработчик API
internal/entity/       Configuration, Field, Rule, Problem и уровни серьёзности
internal/usecase/      контракты и сценарий анализа конфигурации
internal/config/       конфигурация приложения из окружения
internal/cli/          аргументы, запуск анализа, вывод
internal/analyzer/     обход дерева и применение правил
internal/rules/        список правил и отдельные пакеты проверок
internal/rules/helpers/ общие функции правил
pkg/parser/            парсер YAML/JSON
examples/              конфигурации для воспроизведения результатов
scripts/smoke.sh        проверка собранной утилиты
.github/workflows/     CI
```

Проверки основаны на известных именах параметров и значениях. Отсутствие находок
не гарантирует безопасность приложения; конкретные допущения описаны ниже.

## Запуск приложения

```sh
go build -o bin/config-app ./cmd/app
./bin/config-app
```

Один процесс запускает REST на `0.0.0.0:8081` и gRPC на `0.0.0.0:50051`.
Конфигурация загружается один раз, оба сервера используют общий usecase.
Отдельная CLI-команда `cmd/analyzer` продолжает работать независимо.

Ctrl+C или SIGTERM останавливает оба сервера с их собственными таймаутами
завершения. Если один сервер не смог запуститься или завершился с ошибкой,
второй также останавливается, приложение возвращает ошибку.

## HTTP API

Общий запуск REST и gRPC:

```sh
go run ./cmd/app
```

Настройки загружаются в `internal/config` через `cleanenv`.
По умолчанию сервер слушает `0.0.0.0:8081`. Адрес и порт задаются отдельно:

```sh
HTTP_ADDRESS=127.0.0.1 HTTP_PORT=9090 go run ./cmd/app
```

Доступен единственный маршрут `POST /analyze`. Тело запроса —
`multipart/form-data` с обязательным текстовым полем `content`, содержащим
весь YAML или JSON. Экранировать переводы строк и кавычки не требуется.

В Postman выберите **Body → form-data**, добавьте ключ `content` с типом **Text**
и вставьте конфигурацию в Value. Заголовок Content-Type с boundary Postman
сформирует автоматически; вручную его задавать не нужно.

```sh
curl -i http://127.0.0.1:8081/analyze \
  --form 'content=<examples/insecure.yaml'
```

Символ `<` в параметре curl читает файл в текстовое поле; это не загрузка файла.
Можно передать текст непосредственно:

```sh
curl -i http://127.0.0.1:8081/analyze \
  --form-string 'content={"logging":{"level":"debug"}}'
```

Ожидаемый статус — `200 OK`, тело ответа — массив проблем:

```json
[
  {
    "rule_id": "debug-logging",
    "path": "logging.level",
    "severity": "LOW",
    "explanation": "Логирование в debug-режиме.",
    "recommendation": "Поменяйте уровень логирования на info или выше."
  }
]
```

Если находок нет, возвращается `[]`. Наличие проблем не является HTTP-ошибкой.
Значения секретов не включаются в ответ. Содержимое конфига не записывается на диск.

| HTTP-статус | Значение |
| --- | --- |
| `200` | Анализ завершён, возвращён массив проблем |
| `400` | Неверный form-data, отсутствующий/пустой `content` или ошибка разбора конфигурации |
| `404` | Неизвестный путь |
| `405` | Метод, отличный от POST, для `/analyze` |
| `408` | Запрос отменён или истёк его контекст |
| `413` | При чтении запроса превышен лимит 1 MiB |
| `415` | Content-Type отличается от `multipart/form-data` |
| `500` | Внутренняя ошибка анализа |

Ошибки обработчика возвращаются в JSON с полем `error`, без содержимого запроса
и внутренних подробностей. Стандартные ответы роутера `404` и `405` — текстовые.
Дополнительные поля игнорируются. `content` читается только из текстовых полей
тела, не из query-параметров. Загрузка файлов вместо текстового поля не поддерживается.
Лимит 1 MiB относится ко всему multipart-телу, включая служебные заголовки.

Маршрут обработки:

```text
request.Analyze → entity.Configuration → usecase.Configuration.Analyze
    → parser.Parse → analyzer.Analyze → []entity.Problem
    → response.Analyze → JSON
```

DTO находятся в `internal/controller/restapi/request` и `response`, интерфейс
usecase — в `internal/usecase/contracts.go`, реализация — в
`internal/usecase/configuration`. `entity.Configuration` хранит присланный текст;
`config.Config` содержит настройки самого приложения.

POST сам по себе не шифрует данные. Сервер запускается по HTTP; для передачи
секретов по сети потребуется HTTPS, например на reverse proxy.

| Переменная | По умолчанию |
| --- | --- |
| `HTTP_ADDRESS` | `0.0.0.0` |
| `HTTP_PORT` | `8081` |
| `HTTP_READ_TIMEOUT` | `60s` |
| `HTTP_WRITE_TIMEOUT` | `60s` |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` |
| `HTTP_IDLE_TIMEOUT` | `60s` |
| `HTTP_SHUTDOWN_TIMEOUT` | `10s` |

Неустановленные переменные используют значения по умолчанию. Порт должен быть числом
от 1 до 65535, таймауты — положительными длительностями, например `500ms` или
`30s`. Некорректное значение завершает запуск с ошибкой.

При наличии `.env` в текущем рабочем каталоге он читается автоматически.
Если файла нет, используются переменные окружения и значения по умолчанию.
Ошибки чтения или синтаксиса существующего `.env` прерывают запуск.
В используемой версии `cleanenv` значения из `.env` перезаписывают одноимённые
переменные окружения. Для запуска только через окружение уберите `.env`.
Пустые переменные не равнозначны отсутствующим: для значений по умолчанию
удалите переменную из окружения.

Ctrl+C и SIGTERM запускают корректное завершение с ожиданием до
`HTTP_SHUTDOWN_TIMEOUT`.

## gRPC API

В общем `config.Config` добавлена секция `GRPC`; она загружается из `.env`
или окружения вместе с HTTP-настройками:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `GRPC_ADDRESS` | `0.0.0.0` | Адрес прослушивания |
| `GRPC_PORT` | `50051` | TCP-порт |
| `GRPC_MAX_RECV_MSG_SIZE` | `1048576` | Максимальный размер входящего Protobuf-сообщения в байтах |
| `GRPC_SHUTDOWN_TIMEOUT` | `10s` | Время корректного завершения |

Порт — число от 1 до 65535; размер сообщения и таймаут должны быть положительными.
gRPC запускается вместе с REST одной командой:

```sh
go run ./cmd/app
```

Для локальной проверки можно указать адрес и порт:

```sh
GRPC_ADDRESS=127.0.0.1 GRPC_PORT=50051 go run ./cmd/app
```

В Postman создайте gRPC-запрос к `127.0.0.1:50051` без TLS. Reflection включён:
можно загрузить описание с сервера либо импортировать `docs/proto/v1/analyze.proto`.
Выберите `grpc.v1.ConfigService/Analyze` и отправьте:

```json
{
  "content": "logging:\n  level: debug"
}
```

Ответ содержит `problems` с одной находкой `SEVERITY_LOW`. Неверная конфигурация
возвращает `InvalidArgument`, превышение лимита сообщения — `ResourceExhausted`.
Сервер работает без TLS; для защищённого соединения настройка TLS добавляется отдельно.

Ctrl+C и SIGTERM запускают `GracefulStop`: новые RPC больше не принимаются,
активные получают время завершиться. По истечении `GRPC_SHUTDOWN_TIMEOUT`
вызывается `Stop`, который закрывает соединения и прерывает оставшиеся RPC.
Тесты через `bufconn` проверяют запросы, лимит сообщений и оба сценария остановки.

## Правила

| Проверка | Уровень | Условия |
| --- | --- | --- |
| Debug-логирование | LOW | `level: debug` в контексте логирования или явный `log_level` / `logging_level` |
| Открытый пароль | HIGH | Непустое скалярное значение в известном поле пароля |
| Отключённый TLS | HIGH | `tls: false`, `tls_enabled: false`, `tls.enabled: false` или `disable_tls: true` и варианты SSL |
| Отключённая проверка сертификатов | HIGH | `verify_ssl: false`, `tls.verify: false`, `insecure_skip_verify: true` и другие известные варианты |
| Все IPv4-интерфейсы | MEDIUM | `0.0.0.0` или `0.0.0.0:порт` в поле адреса прослушивания |
| Небезопасный алгоритм | HIGH | MD2, MD4, MD5, SHA1, DES, 3DES, TripleDES, DES-EDE3, DES-EDE3-CBC или RC4 в поле алгоритма |

Названия полей находятся в пакетах соответствующих правил, список алгоритмов —
в `internal/rules/algorithm/algorithm.go`. Сравнение точное после нормализации регистра,
дефисов и подчёркиваний. Упоминания алгоритмов в произвольном тексте не ищутся;
например, `description: MD5` не приводит к находке. Поддерживаются скалярные
списки алгоритмов и адресов. Составные имена наборов шифров за пределами списка
не распознаются. HMAC-SHA1 не приравнивается к SHA1.

Пароли не включаются в текст отчёта. Пустые значения и `null` не считаются
открытыми паролями. Полные ссылки `${DB_PASSWORD}`, `{{ vault_db_password }}`,
теги `!vault`, `!env`, `!secret` исключены из этой проверки. Если ссылка занимает
только часть строки, значение считается открытым: `prefix-${DB_PASSWORD}`.
Обычный Ansible YAML с буквальным паролем даёт находку; само использование
Ansible не является исключением. Источники ссылок и содержимое Vault не проверяются.
Хеши в полях паролей не распознаются отдельно и могут давать находку.

TLS-проверки учитывают противоположный смысл флагов включения и пропуска
проверки. Помимо настоящих boolean принимаются буквальные `true/false`,
`yes/no`, `on/off`, `1/0`, в том числе строки. Произвольные строки и шаблоны
не интерпретируются как boolean. Обобщённые `enabled` и `verify` требуют
контекста `tls` или `ssl`.

Для `0.0.0.0` не делается вывод о доступности из интернета: внешний firewall,
reverse proxy и ограничения сети не видны в произвольном конфиге. Находка
предлагает проверить эти ограничения, даже если в файле присутствует ACL.
IPv6 wildcard в эту базовую проверку не входит.

Пути включают индексы массивов; алиасы YAML проверяются по месту использования.
YAML merge (`<<`) пока не разворачивается в эффективные настройки: анализируется
исходное дерево. Сложные YAML-ключи не рассматриваются как имена параметров.

Общие примеры:

```sh
./bin/config-analyzer examples/insecure.yaml
./bin/config-analyzer examples/safe.yaml
```

Для проверки кода завершения запускайте собранный бинарник: `go run` может
возвращать собственный код ошибки вместо кода приложения.

## Расширение правил

`entity.Problem` — одна найденная проблема: идентификатор правила, путь,
уровень LOW/MEDIUM/HIGH, объяснение и рекомендация. Значения секретов в неё
не записываются.

`entity.Rule` — функция `func(entity.Field) []entity.Problem`. Анализатор
передаёт ей ключ, исходный путь, имена родительских полей и узел значения.
Правило возвращает находки или `nil`; оно не должно менять дерево или контекст.
Анализатор не импортирует пакет правил и ничего не знает о конкретных проверках.

Чтобы добавить штатную проверку:

1. Создайте пакет `internal/rules/<имя>` с функцией `Check` указанной сигнатуры.
2. Объявите варианты имён в этом пакете через `helpers.NewNames`; общие функции
   сопоставления находятся в `internal/rules/helpers`.
3. Добавьте тесты в каталог нового пакета.
4. Подключите функцию в `Default()` в `internal/rules/default.go`.

Обход дерева, парсер и CLI при этом менять не требуется. Для альтернативного
набора проверок можно передать свои функции непосредственно в `analyzer.Analyze`.
`Default()` каждый раз возвращает отдельный список; локальная замена правила
не изменяет стандартный набор.

Расширяемость проверяется тестом `TestAnalyzeWithAdditionalRule`: правило
HttpOnly объявлено только в тестовом пакете и подключается к штатным проверкам.
Проверяются JSON и YAML, вложенные массивы, путь находки, рекомендация и
сохранение результатов существующих правил. Это тестовая проверка, в CLI её нет.

Парсер пока использует `yaml.Node` как общее представление JSON и YAML.
Для нового формата потребуется адаптер к этому дереву либо отдельное изменение
модели данных; автоматической поддержки произвольных форматов сейчас нет.

## Парсер

`parser.Parse(io.Reader)` возвращает документ с определённым форматом (`json`
или `yaml`) и корневым `yaml.Node`. Такое представление сохраняет теги (включая
Ansible `!vault`), порядок полей и позиции в исходном документе.

Сначала проверяется валидность JSON; иначе ввод разбирается как YAML. Поэтому
невалидный JSON, допустимый в YAML, принимается как YAML. Разрешён любой тип
корня, в том числе число `5`, строка, массив и `null`. Пустой ввод, повторяющиеся
скалярные ключи, рекурсивные алиасы и несколько документов в одном потоке приводят
к ошибке. Парсер не закрывает переданный поток.

```go
import "github.com/MaksimovYuriy/ConfigAnalyzer/pkg/parser"

doc, err := parser.Parse(reader)
if err != nil {
    return err
}
```
